### 01-sandbox-isolation — partial

**Why:** The matrix never exercises the sandbox. securityZipSlipTraversalBlocked (L30-58) calls StagedExtraction.secureSymlinks on a hand-made folder: it is a discipline-08 symlink-containment test and touches neither SandboxProfile, sandbox-exec nor CommandRunner. securityZeroCommandLinePasswordExposure (L62-91) only inspects the argv arrays returned by SevenZipCommand.create/add/extract (L69-84) and the bytes returned by passwordInput (L87-90); it never runs ProcessBox (CommandRunner.swift:198-214), so it does not prove the password actually reaches 7zz on stdin, that every AppModel call site passes `input:`, or that sandbox-exec's own argv (profile text + -D params) stays password-free. Nothing in the matrix asserts (deny network*), the read-denylist, or that AppModel.confined (AppModel.swift:1462-1465) wires the profile in. The only real sandbox proof in the repo is outside the matrix: SandboxTests.swift L54-85 (live write-deny + /private resolution via temporaryDirectory). There is no live read-deny or network-deny test anywhere.

**How to strengthen:** (1) Live stdin delivery: `CommandRunner(executableURL: /bin/cat).run([], input: SevenZipCommand.passwordInput(secret))` and assert stdout == secret+"\n" repeated 4 times; add the negative: `run` with input nil gives empty stdout (nullDevice). (2) Argv-wide scan: for every builder (list/test/extract/create/add/delete/rename/hash/compressTarStage) assert `!args.joined(separator: "\u{0}").contains(secret)` and that `profile.launchArguments(...)` for a password-carrying command also lacks it. (3) Live read-deny using the `home:` injection point: create tempHome/.ssh/key, `forOperation(archive: tempHome/Downloads/x.7z, writable: [], home: tempHome)`, run `7zz h -- tempHome/.ssh/key` under `plain.sandboxed(profile)` and expect exitCode != 0, then the same file outside the denylist succeeds. (4) Live network-deny: CommandRunner is executable-agnostic, so `CommandRunner(executableURL: /usr/bin/nc, sandbox: profile).run(["-z","-w1","127.0.0.1",port])` against a listening socket must fail while the unsandboxed runner succeeds. (5) Wiring: an ArhivarAppTests case that, with settings.sandboxEngine == true, checks `model.confined(runner, archive:)` returns a runner whose `sandbox != nil` and whose profile denies the personal dirs, and with the setting false returns the plain runner.

### 02-hierarchy-stress — partial

**Why:** stressMassiveHierarchyAndBreadth (Tests/ArhivarCoreTests/ChaosAndSecurityMatrixTests.swift L98-124) does drive the real production path: a synthetic `7zz l -slt` text with 2036 entries goes through ListingParser.parse (L115) and ArchiveTree.build (L119), which recurses in `convert`. But it cannot prove the architectural claim: (a) 35 levels (L108) is below ArchiveTree.maxDepth = 100 (Sources/ArhivarCore/ArchiveTree.swift:66) and far below the thousands that overflowed before the cap (ArchiveTreeDepthTests uses 5000 components) — deleting the clamp at ArchiveTree.swift:80 leaves this test green; (b) it never calls index / sorted / search / contents, the recursive consumers the cap exists for and which AppModel always runs after build (Sources/Arhivar/AppModel.swift:145 `nodeIndex = ArchiveTree.index(tree)`, :1605 `ArchiveTree.sorted`); (c) L122 `tree.count == 2001` checks only the root count — the depth-36 leaf (`d1/…/d35/leaf.txt`) is never looked up, so a build that silently drops or mis-nests deep entries still passes; (d) L123 `#expect(elapsedTree < 1.0)` is a hardcoded wall-clock bound: measured ~10 ms for 2036 entries, ~100x headroom, so it proves nothing and contradicts the repo's own convention (Tests/ArhivarCoreTests/ListingPerformanceTests.swift:5 'no time-dependent fragile assertion'). stressRapidParsingThroughput (L128-156) parses a 3-entry sample 50 times — 150 entries, no size, no timing — which is tautological for 'fast list parsing' (pure function determinism). The only real throughput evidence is ListingPerformanceTests.parsesLargeListingQuickly (200k entries; prints 5.2 s in a debug build; asserts nothing about time).

**How to strengthen:** (1) Remove L123. Add structural checks on the built tree: `let index = ArchiveTree.index(tree)`; `#expect(index[deepPath + "/leaf.txt"] != nil)`; `#expect(treeDepth(tree) == 36)` (reuse the iterative helper from ArchiveTreeDepthTests); `#expect(ArchiveTree.search(tree, query: "leaf").count == 1)`; `#expect(ArchiveTree.sorted(tree, using: [ArchiveTree.nameComparator]).count == 2001)`; put the 2000 files under one folder `wide/` and `#expect(ArchiveTree.contents(of: "wide", roots: tree, index: index).count == 2000)`. (2) For depth, generate `ArchiveTree.maxDepth + 50` levels and assert `treeDepth(tree) == ArchiveTree.maxDepth` and that sorted/search/index complete — so removing the clamp fails the matrix test instead of only the dedicated depth test. (3) For throughput, either parse `syntheticListing(count:)` at 20k and 200k and assert a scaling ratio (e.g. t200k / t20k < 25, CI-robust and detects super-linear regressions), or keep timing report-only and assert `entries.count == 200_000` plus `allSatisfy { $0.modified != nil }`; the current 3-entry x 50 loop should be deleted or renamed as an idempotence test.

### 03-malformed-data — partial

**Why:** destructiveCorruptedArchiveHandling (Tests/ArhivarCoreTests/ChaosAndSecurityMatrixTests.swift L163-187) does run the real 7zz binary, which is good, but its assertions do not prove the typed-error claim: L176 and L186 use `#expect(throws: SevenZipError.self)`, which also passes for `.wrongPassword`, `.cancelled` (exit 255) or `.failed`; only the 0-byte case checks `needsPassword == false` (L175), so a garbage file that the classifier turned into a password prompt would still pass. L174/L185 (`exitCode != 0`) are trivial. L180-181 use unseeded `UInt8.random`, contradicting the repo's seeded SplitMix64 convention in FuzzTests.swift L10-20 and the global fragile-test rule (a random 2-byte signature such as PK/1F8B/BZ/MZ changes 7zz's code path). The docstring (L160-162) claims 'header bytes randomly corrupted', yet no real archive is ever corrupted or truncated: the `ERRORS:/Unexpected end of archive` paths (which classify differently: `.failed(2)` for zip/tar, `.notArchive` for 7z) are untested. L168 builds a plain `CommandRunner` without `SandboxProfile`, whereas production lists through `AppModel.confined` (AppModel.swift L522, L1462-1465) under sandbox-exec, so launcher failure modes (exit 65/71, errno=1) are not exercised. L164 silently returns when the engine is missing, so the test passes vacuously on a machine without Vendor/7-Zip/7zz. AppModel.handle/message(for:) (AppModel.swift L1514-1560) are never touched; the only app-level corrupt-archive coverage is AppModelTests.swift L281-306 (a CRC-corrupted stored zip via extractHere).

**How to strengthen:** 1) Assert the exact case: `#expect(throws: SevenZipError.notArchive)` for both the 0-byte and the garbage file, plus `#expect(!SevenZipError.needsPassword(resGarbage))`. 2) Replace `UInt8.random` with the seeded SplitMix64 from FuzzTests and iterate several seeds, also prefixing real signatures ("PK\u{03}\u{04}", "7z\u{BC}\u{AF}'\u{1C}", "\u{1F}\u{8B}", "Rar!\u{1A}\u{07}\u{01}\u{00}", 257-byte 'ustar' header) so format-specific parsers are hit. 3) Add real corruption: create good.zip/.7z/.tar with 7zz, then truncate at the tail (-40 B), at the midpoint and (tar) strip the 1024 trailing zero blocks, and flip seeded bytes in the header region; for each assert `check` throws and that the thrown `.failed` message contains a human-readable reason (e.g. 'Unexpected end of archive') — this would have caught the header-only `ERRORS:` message. 4) Run the listing through `runner.sandboxed(.forOperation(archive: url, writable: []))` to match production. 5) Use `@Test(.enabled(if: engineURL != nil))` instead of the silent `return`. 6) Add an AppModel-level test: `openArchive(garbage)` then await `operationTask` and assert `alert?.message == t(.errorNotArchive)`, `listing == nil`, `operation == nil`, `passwordRequest == nil`.

### 06-endurance-leaks — partial

**Why:** enduranceStagingLifecycleCycles (Tests/ArhivarCoreTests/ChaosAndSecurityMatrixTests.swift:230-248) does drive the real StagedExtraction.makeStagingDirectory (L235) and StagedExtraction.removeTree (L245) on genuine 0o555/0o444 content (L242-243), so it is not tautological, and 30 cycles nominally meets 'dozens'. But the only assertions are fileExists(staging) == true (L236) and == false (L246). The claim is 'no handle or permission leaks', and neither is measured: (1) nothing on the exercised path opens a descriptor (makeStagingDirectory is url(for:.itemReplacementDirectory) at StagedExtraction.swift:13-15; removeTree is removeItem + OwnerAccess.addTree + removeItem at :281-285, all chmod/unlink), so an fd leak could not be observed even in principle, and the real fd-bearing components (CommandRunner pipes, isMacMetadata's FileHandle at StagedExtraction.swift:68, entries(ofDirectory:)'s opendir at :77) are never touched; (2) removeTree deletes instead of restoring, so 'permission leak' is vacuous for this path - the restore code (OwnerAccess.granting :444-454, secureSymlinks' restore :207, addTree/restore ordering :426-440) is not under cycle; (3) the fallback branch '.arhivar-staging-<UUID>' (:19-21) is never taken because itemReplacementDirectory always succeeds on the boot volume; (4) nothing asserts that the parent TemporaryItems dir does not accumulate NSIRD_* entries, which is the only place a staging 'leak' on this path could show up; (5) no symlink-to-outside directory inside the tree, so a regression in addTree's lstat/S_IFLNK guard (:428) that chmods a user's real folder would pass. It is essentially a 30x loop of HardeningTests.removeTreeDeletesReadOnlyFolders (HardeningTests.swift:323-332) with a shallower tree (that test also covers a 0o000 dir). Related: AppModelTests.swift:308 checks only for '.arhivar-staging' leftovers in the workspace, but on the boot volume staging lands under $TMPDIR/TemporaryItems/NSIRD_*, so that leftover assertion is vacuous for the primary branch too.

**How to strengthen:** Keep the loop but make each cycle observable: (a) snapshot the count of entries in staging.deletingLastPathComponent() (the TemporaryItems parent) before the loop and assert it is unchanged after, so an un-removed NSIRD_* dir fails the test; (b) snapshot FileManager.default.contentsOfDirectory(atPath: "/dev/fd").count before/after and, when engineURL is available, run a real CommandRunner.run(SevenZipCommand.extract(...)) into the staging plus StagedExtraction.destination(for:..., mode: .smart) with a '._x' file present (forces the FileHandle path at StagedExtraction.swift:68) and secureSymlinks on the tree, then assert the fd delta is 0 (allow a 2.5 s sleep if a cancel path is included, because ProcessBox.terminate's asyncAfter at CommandRunner.swift:225 holds the pipes for killGracePeriod); (c) exercise the fallback branch by passing a FileManager subclass whose url(for:in:appropriateFor:create:) throws and assert the result name has prefix '.arhivar-staging-', mode is 0o700, and removeTree removes it; (d) inside the tree add a 0o000 directory nested in a 0o555 one and a symbolic link to an external 0o555 directory, and assert after removeTree that the external directory still exists with mode 0o555 (proves addTree never follows links); (e) add a Finder-locked file (chflags UF_IMMUTABLE) case and assert the documented contract (either full removal after clearing flags, or the tree and its original modes left intact) - today it does neither, see findings.

### 09-parser-fuzz — tautological
